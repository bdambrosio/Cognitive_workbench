# Factorio game-embodiment subproject

Server + bridge for the Jill v1 experiment. Design:
`docs/factorio-bridge-architecture.md`. Separate subproject — not part
of M1/M2 measurement.

## Server

Factorio 2.0.73 headless (Docker), base game only (no Space Age DLC —
matches FLE), enemies disabled, 1024×1024 map, RCON on localhost only.

```bash
cd factorio
docker compose up -d        # save auto-generates on first run
docker compose logs -f
```

- Game port: `34197/udp` on all interfaces — join from a Factorio 2.0.73
  client at `<this-host>:34197` (LAN visibility, no password).
- RCON: `127.0.0.1:27015`, password in `data/config/rconpw`
  (gitignored). FLE hardcodes its RCON password as a module constant;
  patch `fle.env.instance.RCON_PASSWORD` before constructing
  `FactorioInstance` (see `smoke_fle.py`).
- `data/` is owned by the container's `factorio` user; edit files in it
  via `docker exec -u root jill-factorio ...`.

## Python / FLE

Dedicated venv (do not mix with the CW environment):

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python smoke_fle.py    # step-1 smoke: place + connect_entities
```

The smoke is self-cleaning (picks up its own artifacts) and
non-destructive (`clear_entities=False`, keeps the save's tech state).

## Gotchas learned in step 1

- The docker image ships Space Age enabled by default; `DLC_SPACE_AGE=false`
  in the compose env is the supported off switch (the entrypoint rewrites
  `mods/mod-list.json`, so editing that file directly does not stick).
- FLE 0.4.3 breaks with a2a-sdk ≥ 1.0 (`TextPart` import) — pinned.
- `connect_entities` validates semantics, not just geometry: a
  furnace→furnace belt is rejected with "add an inserter" — use
  inserters as endpoints, or positions for bare belt runs.
- `FactorioInstance` defaults are host-hostile (`clear_entities=True`,
  `all_technologies_researched=True`, `fast=True`); the bridge must
  override all three for human-coexistent play. `coexist_fle.py`
  (step 2) shows the safe character spawn.

## The fle-bridge mod (step 2b)

Generated by `build_mod.py` from the installed fle package into
`fle-bridge/` (mounted into the container via docker-compose). Actions
are exposed as `remote.call("fle_bridge", "call", "<action>", ...)`;
`storage` stays data-only, so saves/autosaves/joins work. Ported as of
0.2.1: get_entity, get_entities, nearest, place_entity,
place_entity_next_to, move_to (+ request_path/get_path pipeline),
harvest_resource, insert_item, extract_item, craft_item, pickup_entity,
rotate_entity, connect_entities (Lua side; Python resolvers come with
the bridge), set_inventory, plus the human-safe
create_agent_characters. Walking/harvest tick handlers are statically
registered and pcall-guarded.

0.3.0 adds game-chat capture: `on_console_chat` → data-only ring
buffer in `storage.chat` (cap 200, monotonic seq); poll with
`get_chat(since_seq)`; `say(message)` prints as blue "Jill: …" and
appends itself to the buffer (game.print does not fire
on_console_chat, so no loop). Verified live 2026-07-14 (human chat
captured, say visible in client, saves clean).

When remote.call args go through `/silent-command`, encode them with
`json.dumps(..., ensure_ascii=False)` — JSON's `\uXXXX` escapes are
invalid Lua string escapes (bare `\u` errors).

- After editing `build_mod.py`: bump `MOD_VERSION` (on_configuration_changed
  only fires on version change), regenerate, `docker compose restart`.
- **Human clients need the mod too** (Factorio requires matching mods and
  fle-bridge is not on the mod portal). Re-zip to the local client after
  each version bump:
  `cp -r fle-bridge fle-bridge_<V> && zip -qr ~/.factorio/mods/fle-bridge_<V>.zip fle-bridge_<V> && rm -rf fle-bridge_<V>`
  (delete the old zip first — two versions of the same mod confuse the picker).
- The mod's `storage` is isolated from the level state: `/sc` cannot
  reach `storage.agent_characters` etc. directly — everything goes
  through the remote interface. This is the intended boundary.
- Mod event-handler errors are non-recoverable and kill the server —
  no dynamic `script.on_nth_tick` registration (that's why init_data
  forces `storage.fast = true`); tick work belongs in statically
  registered handlers that never error.

## The bridge process (step 3)

`bridge/` — the peripheral-pattern process from the architecture note:
FastAPI on `localhost:3004`, RCON to the mod's remote interface,
policy allowlist (`bridge/policy.py`), observation cache + deviation
classifier (world_changed / stale_model / infeasible), ~10 s telemetry
cache, chat relay with the below-the-LLM "Jill, stop" watcher.

```bash
.venv/bin/python -m bridge            # serve (from factorio/)
.venv/bin/python verify_bridge.py     # step-3 acceptance: smelting
                                      # column over HTTP + one forced
                                      # deviation of each class
```

Gotchas learned in step 3:

- Factorio 2.0 directions are 16-step: 0=N, 4=E, 8=S, 12=W (not the
  1.1-era 0/2/4/6).
- Pathfinding needs a clearance ladder (entity_size 1.5→0.25, cribbed
  from FLE's connect client): a start position adjacent to entities
  fails at full character size. Applied in both /act/walk and
  /act/connect.
- `place_entity` enforces character reach; `place_entity_next_to` does
  NOT (FLE inconsistency, observed live). Don't rely on next_to for
  reach realism.
- Water/cliffs are tiles, not entities — an entity-empty area is not
  necessarily buildable or walkable (`get_tile(...).collides_with`).
- mod 0.4.x: move_to always takes the walking queue (real walking at
  1x, visible presence); `storage.fast` stays true for the synchronous
  semantics of every other action. `agent_position` / `stop` /
  `get_alerts` back /status, /act/stop and the telemetry poll.

## CW-side tools (step 4)

`src/tools/fac-*/` — 13 chat tools (react_invoke pattern), all HTTP via
the one canonical client `src/utils/factorio_link.py` (`FACTORIO_URL`,
default `http://localhost:3004`): fac-status, fac-observe (status +
observe + telemetry composition), fac-inventory, fac-walk, fac-place,
fac-connect, fac-insert, fac-extract, fac-craft, fac-harvest,
fac-rotate, fac-say, fac-stop. Deviation reports pass through verbatim
in the returned text. Tests: `tests/test_fac_tools.py` (discovery scan
+ mocked-bridge smokes, no server needed).

## Sensor + scenario (step 5)

- `src/sensors/factorio-telemetry/` — event ingress: game chat from
  others (no addressing filter; Jill judges), joins/leaves, watched
  flow stops (`watch_items`), new alert kinds. Plain-text results so
  events arrive as chat-loop turns; first run baselines silently;
  state in `~/.cache/cognitive/factorio-telemetry/state.json`.
- `scenarios/jill-factorio.yaml` — junior-factory-engineer role +
  norms, the one durable assignment concern (iron-plate health,
  rhythm 1h), tick + factorio-telemetry sensors. Run:
  `python src/launcher.py scenarios/jill-factorio.yaml --autonomy`
  (server and bridge must be up first).
- "Jill, stop" wiring verified end-to-end: the phrase in game chat
  aborts an in-flight /act/walk with deviation kind=stopped, below
  the LLM.
- Bridge /telemetry alerts are deduped to one live alert per
  (entity, issue, position), expired after 10 min quiet.
- Tests: `tests/test_factorio_sensor.py` (mocked bridge; event
  classes, self-chat skip, bridge-down).

## Step-2 finding: NEVER run FLE injection against this server

FLE's runtime injection puts Lua functions into `storage`. Factorio
cannot serialize functions, so the next save/autosave/player-join
**fails non-recoverably and crashes the headless server**; docker
restarts it from the last good save and the world silently regresses
(this looked like "my entities vanished" until we caught
RestartCount=4). Fix in progress per the architecture note: the
`fle-bridge` mod (data/mods/) exposing the cribbed actions as
`remote.call` interfaces, keeping `storage` data-only. Until that
lands, only direct data-only RCON (`surface.create_entity` etc.) is
safe on the shared world — smoke_fle.py/coexist_fle.py are for
disposable worlds only.

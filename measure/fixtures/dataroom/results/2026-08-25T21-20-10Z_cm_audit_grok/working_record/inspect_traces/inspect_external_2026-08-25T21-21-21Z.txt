74|### AI Ticketing
75|
76|Tickets are raised from a conversation (by the AI or an agent), or from an alert
77|webhook. Each one is triaged, deduplicated against open tickets, and then
78|investigated: the AI proposes hypotheses, tests each against your connected
79|tools, and records every query it ran as evidence you can inspect. The result is
80|a versioned root-cause analysis with citations back to that evidence.
81|
82|Connect read-only investigation sources under **Settings → Ticketing**:
83|observability platforms via MCP (Grafana, Elasticsearch, Sentry, CloudWatch, or
84|any MCP server), and optionally a **guardrailed SQL connector** (Postgres/MySQL,
85|direct or over an SSH tunnel).
86|
87|**Autonomy is staged, and you choose the level:**
88|
89|| Level | The AI can |
90||-------|-----------|
91|| **L1** | Investigate and document only |
92|| **L2** | Also propose a resolution — a human approves or rejects it |
93|| **L3** | Also message the customer and close the ticket, behind confidence guards |
94|
95|#### Guardrails
96|
97|The investigation agent reads untrusted customer text and holds live tool
98|access, so the limits are enforced in code, not by prompting:
99|
100|- **The SQL connector is read-only, structurally.** Queries are parsed to an AST
101|  and rejected unless they are a single plain `SELECT`. Writes, DDL, multiple
102|  statements, and a denylist of dangerous functions cannot pass. Table access is
103|  restricted to an allowlist you pick, enforced through CTEs, joins and
104|  subqueries. A `LIMIT` is forced. Comments are stripped before execution, since
105|  MySQL executes `/*! */`. The connection itself is a read-only transaction with
106|  a statement timeout — a second, independent barrier.
107|- **Columns you mask are never readable.** Masked columns are blocked from being
108|  referenced anywhere, including in a `WHERE` clause, so their values can't be
109|  probed; whole-row tricks that would smuggle them out (`to_jsonb(t)`, `t::text`,
110|  `to_json(t.*)`) are blocked too, and results are masked again on the way back.
111|- **Nothing is written to your database, ever.** Approving an AI proposal records
112|  the decision — any change to your systems is made by your team.
113|- **Row-level scoping keeps one customer's data out of another's ticket.** Mark
114|  the column that identifies the customer on any table holding per-customer rows
115|  (`orders → customer_email`). Queries against it are rewritten to read only the
116|  ticket customer's own rows — the AI cannot widen that, because the filter is
117|  applied to the table it selects *from*, not to a condition it could write
118|  around. A ticket with no known customer cannot query a scoped table at all,
119|  rather than falling back to reading everything. Tables you leave unscoped
120|  (products, error codes) stay fully readable.
121|- **Cross-customer isolation on outbound messages.** Identifiers belonging to
122|  anyone other than the recipient are stripped from every message sent to a
123|  customer, and other customers' tickets are redacted before they reach the
124|  model — a second line behind row scoping.
125|- **Every query is audited.** Each attempt is logged with the SQL and outcome;
126|  returned rows are deliberately never stored.
127|
128|> **When you connect a database:** set a row-scope column for every table that
129|> holds per-customer rows — it's the control that stops the agent reading across
130|> customers, and it's off until you set it. Point the connector at a service
131|> account restricted to what support genuinely needs, and prefer views that are
132|> already scoped.

389|### Background processors
390|
391|The API server only enqueues long-running jobs — a separate worker process
392|executes them. If no worker is running, jobs sit at `pending` forever and the
393|UI shows a progress bar that never advances.
394|
395|| Worker | Command | Handles |
396||---|---|---|
397|| Knowledge + FAQ | `python -m app.workers.run_knowledge_processor` | Knowledge ingestion (crawl, PDF, sitemap) **and** FAQ jobs |
398|| Ticket investigator | `python -m app.workers.ticket_investigator` | AI ticket investigation + ticket lifecycle |
399|| CRM sync | `python -m app.workers.crm_sync` | Lead push to HubSpot / Pipedrive |
400|
401|Run each from the `backend/` directory with the virtualenv active.
402|
403|**FAQ / Help Center processor.** FAQ generation and import jobs (Generate FAQs,
404|"Migrate an existing help center", PDF import) are drained by the *knowledge
405|worker* — there is no separate FAQ container. Both knowledge entrypoints pick
406|up the FAQ queue, so either one is enough:
407|
408|```bash
409|# Recommended for local dev — knowledge and FAQ in one loop
410|python -m app.workers.run_knowledge_processor
411|
412|# What Docker runs: knowledge and FAQ as independent asyncio tasks, so a long
413|# FAQ generation never blocks knowledge ingestion
414|python -m app.workers.knowledge_processor
415|
416|# FAQ queue only — useful when debugging generation/import in isolation
417|python -m app.workers.faq_processor
418|```
419|
420|Polls every 60s. On startup it fails any job left stuck in `processing` by a
421|previous crash, so a killed worker doesn't strand a job forever.
422|
423|**Ticket investigator.** Runs two loops in one process — investigation runs
424|(polled every 15s) and ticket lifecycle/SLA sweeps (every 5 min):
425|
426|```bash
427|python -m app.workers.ticket_investigator
428|```
429|
430|Needs Redis (`REDIS_URL`) to push live `ticket_update` frames to dashboard

538|
539|**What is ChatterMate?**
540|ChatterMate is an open-source AI customer support platform. It combines an AI chatbot (trained on your knowledge base) with human agents in a shared inbox, so AI handles routine questions 24/7 and hands off to your team when it matters.
541|
542|**Is ChatterMate free and open source?**
543|Yes. The core platform is Apache-2.0 licensed — free for personal and commercial use, including self-hosted production deployments. There's also a free hosted plan at [app.chattermate.chat](https://app.chattermate.chat).
544|
545|**Can the AI hand off conversations to a human agent?**
546|Yes — human handoff is a core feature, not an add-on. ChatterMate detects frustration or explicit requests for a human and transfers the conversation with full context, respecting business hours and agent availability.
547|
548|**Does ChatterMate work with Shopify?**
549|Yes. Install it from the [Shopify App Store](https://apps.shopify.com/chattermate-chat) to answer order-status, shipping, and product questions directly from your store data. The widget also embeds on any other e-commerce or website platform with one line of code.

552|Yes. Download the [WordPress plugin](https://github.com/chattermate/chattermate-wordpress-plugin/releases/latest/download/chattermate-chat.zip), install it via **Plugins → Add New → Upload Plugin**, then enter your Widget ID under **Settings → ChatterMate Chat**. The chat launcher appears on your site with no theme edits. A WordPress.org directory listing is in progress.

554|**Can I self-host ChatterMate?**
555|Yes. Run the full stack (Postgres, Redis, backend, frontend) on your own infrastructure with `npm install -g chattermate-deploy` — see [Quick Start](#quick-start). Self-hosting gives you complete data ownership.

558|OpenAI, Anthropic (Claude), Google Gemini, Mistral, xAI (Grok), DeepSeek, and Groq — bring your own API key, or enter a custom model ID for any model a provider supports. You can switch providers at any time without code changes.

OK: 1|# Help Center hosting — infrastructure runbook
2|
3|The public help center is served by the backend itself (host-dispatched SSR —
4|see `backend/app/core/help_center_host.py`). This runbook covers the
5|deploy-time pieces that live **outside** the repo: DNS, TLS and the host
6|nginx on the production VPS. `frontend/nginx.conf` and the docker-compose
7|files need **no changes**.
8|
9|> **As deployed on the ChatterMate cloud VPS (2026-07-14):** the base domain is
10|> **`help.chattermate.chat`** (orgs serve at `{slug}.help.chattermate.chat`), not
11|> the `chattermate.help` this doc originally planned — that domain was never
12|> registered, and the org only owns `chattermate.chat`. DNS is **Route53**, so the
13|> wildcard cert is issued and auto-renewed with the `dns-route53` plugin.
14|> Placeholders (`<VPS_IPV4>`, `<ZONE_ID>`, …) stand in for the live values; the
15|> real ones live on the VPS and in ops notes, not in this public repo.
16|
17|## 1. One-time platform setup
18|
19|### DNS (Route53)
20|Point a wildcard under the domain you own at the VPS. On the cloud box this is
21|the `chattermate.chat` hosted zone (`<ZONE_ID>`):
22|- `*.help.chattermate.chat.  A     <VPS_IPV4>`
23|- `*.help.chattermate.chat.  AAAA  <VPS_IPV6>`
24|
25|One wildcard record covers every org — no per-org DNS. Create them via the API:
26|```bash
27|aws route53 change-resource-record-sets --hosted-zone-id <ZONE_ID> \
28|  --change-batch file://wildcard.json   # UPSERT A + AAAA for *.help.<domain>
29|```
30|
31|Backend env (`backend.env` on the VPS):
32|```
33|HELP_CENTER_BASE_DOMAIN=help.chattermate.chat
34|HELP_CENTER_TARGET_IPS=["<VPS_IPV4>"]   # JSON array — see gotcha below
35|```
36|> **Gotcha:** `HELP_CENTER_TARGET_IPS` is a `frozenset` setting, so
37|> pydantic-settings JSON-parses the env value. A bare IP or comma list
38|> (`<VPS_IPV4>`) fails validation and crash-loops the backend at startup —
39|> it **must** be a JSON array: `["<VPS_IPV4>"]`. (Powers the per-org
40|> custom-domain A-record verification in §2; unused by the wildcard site.)
41|
42|### Wildcard certificate (DNS-01 via Route53)
43|HTTP-01 cannot issue wildcards. A dedicated IAM user with the standard certbot
44|Route53 policy (`route53:ListHostedZones` + `GetChange` on `*`,
45|`ChangeResourceRecordSets` on the zone) has its creds at `~/.aws/credentials`
46|(mode 600) on the box. Issue once:
47|```bash
48|docker run --rm \
49|  -v ~/chattermate/certbot/conf:/etc/letsencrypt \
50|  -v ~/.aws:/root/.aws:ro \
51|  certbot/dns-route53 certonly --dns-route53 \
52|  -d '*.help.chattermate.chat' -d 'help.chattermate.chat' \
53|  --cert-name help.chattermate.chat \
54|  --non-interactive --agree-tos -m <ops-email>
55|```
56|
57|**Auto-renewal:** a daily cron runs the compose `certbot` service as a
58|**one-shot**, then reloads nginx only if a cert actually changed:
59|```bash
60|docker compose -f docker-compose.hostinger.yml \
61|  run --rm --entrypoint certbot certbot \
62|  renew --quiet --deploy-hook "echo reload-needed > /var/www/certbot/.reload"
63|# ...then, if the flag file appeared: rm it && docker compose exec -T nginx nginx -s reload
64|```
65|It uses the `certbot/dns-route53` image and mounts
66|`/home/chattermate/.aws:/root/.aws:ro`, so the wildcard renews unattended (the
67|renewal conf remembers `authenticator = dns-route53`). Existing HTTP-01 webroot
68|certs still renew — the dns-route53 image is a superset of `certbot/certbot`.
69|`renew` covers every cert in the shared `certbot/conf`, not just the wildcard.
70|
71|> **The `certbot` service must stay one-shot — never give it a long-running
72|> loop entrypoint.** It previously used
73|> `sh -c 'trap exit TERM; while :; do certbot renew; sleep 12h & wait ${!}; done;'`,
74|> which broke renewal in two non-obvious ways:
75|>
76|> 1. **`compose run` inherits the entrypoint.** The "one-off" cron run never
77|>    exited, so `--rm` never fired (a container leaked *every night*) and the
78|>    cron's chained `&& nginx -s reload` never ran at all.
79|> 2. **`sh -c '<script>' <args>` silently discards the args** (they land in
80|>    `$0`/`$1`…, which the script ignores). So it renewed *without* the
81|>    `--deploy-hook`, every 12h — beating the daily cron to the renewal. The
82|>    cron's own `renew` then found nothing due, so the hook never fired.
83|>
84|> Net effect: certs renewed on disk while **nginx kept serving the old ones**,
85|> masked only by deploys happening to restart nginx. Left alone that expires a
86|> live cert. The service is therefore declared with no `entrypoint:` (the
87|> image's default is `certbot`) and `profiles: ["tools"]`, so `compose up -d`
88|> never starts it while `compose run` still works (it auto-enables the profile).
89|>
90|> Regression check — the command must **exit** and leave nothing behind:
91|> ```bash
92|> timeout 60 docker compose -f docker-compose.hostinger.yml \
93|>   run --rm --entrypoint certbot certbot renew --quiet   # ~3s, rc=0
94|> docker ps -a --filter name=certbot   # must be empty
95|> ```
96|
97|### Host nginx server block
98|Lives at `~/chattermate/nginx/conf.d/help-center.conf` (mounted read-only into
99|the `chattermate-nginx-1` container). `proxy_set_header Host $host` is what
100|makes backend host-dispatch resolve the org. Upstream is the compose service
101|name `backend:8000` (nginx shares the `chattermate-network`), not a published
102|host port.
103|
104|```nginx
105|# {slug}.help.chattermate.chat
106|server {
107|    listen 443 ssl http2;
108|    server_name *.help.chattermate.chat help.chattermate.chat;
109|    ssl_certificate     /etc/letsencrypt/live/help.chattermate.chat/fullchain.pem;
110|    ssl_certificate_key /etc/letsencrypt/live/help.chattermate.chat/privkey.pem;
111|    include /etc/nginx/conf.d/ssl-params.conf;
112|
113|    location / {
114|        proxy_pass http://backend:8000/;
115|        proxy_set_header Host $host;
116|        proxy_set_header X-Real-IP $remote_addr;
117|        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
118|        proxy_set_header X-Forwarded-Proto $scheme;

120|}

123|    listen 80;
124|    server_name *.help.chattermate.chat help.chattermate.chat;
125|    location /.well-known/acme-challenge/ { root /var/www/certbot; }

12|## 1. Purpose
13|
14|Body is the onboard software stack for a differential-drive robot chassis. It provides sensor acquisition, motor control, and safety supervision as a set of independent communicating processes linked by Zenoh. The desktop agent (Jill, running on the CW workstation) connects to the same Zenoh network and interacts with Body exclusively through published topics. Body has no knowledge of Jill's internals; Jill has no knowledge of Body's process structure. The Zenoh topic schema defined in this document is the contract between them.

80|### 3.2 Design Principles
81|
82|- Each process is a standalone Python script with its own `main()` and Zenoh session.
83|- No shared memory, no threading across process boundaries.
84|- Processes do not import each other. The Zenoh topic schema is the only coupling.
85|- Every process logs to stdout. The launcher captures and tags output.
86|- Every process handles SIGTERM gracefully: releases hardware, closes Zenoh session, exits.
87|- Motor output defaults to zero (stopped) on startup and on any error.

131|## 5. Message Schemas
132|
133|All messages are JSON-encoded UTF-8 strings published as Zenoh values. Timestamps are Unix epoch float (seconds with microsecond precision). All spatial units are SI: meters, radians, meters/second, radians/second.
134|
135|### 5.1 `body/cmd_vel` (Jill → motor_controller)
136|
137|Twist command in robot body frame. Linear is forward/back, angular is rotation (positive = counterclockwise viewed from above).
138|
139|```json
140|{
141|  "ts": 1713264000.123456,
142|  "linear": 0.2,
143|  "angular": 0.0,
144|  "timeout_ms": 500
145|}
146|```
147|
148|- `linear`: m/s, positive = forward. Clamped by motor_controller to hardware limits.
149|- `angular`: rad/s, positive = CCW.
150|- `timeout_ms`: if no new `cmd_vel` arrives within this window, motor_controller sets output to zero. Safety backstop independent of watchdog.
151|
152|### 5.2 `body/cmd_direct` (Jill → motor_controller)
153|
154|Direct wheel velocity command. Bypasses twist-to-differential math. For calibration and testing.
155|
156|```json
157|{
158|  "ts": 1713264000.123456,
159|  "left": 0.15,
160|  "right": 0.15,
161|  "timeout_ms": 500
162|}
163|```
164|
165|- `left`, `right`: m/s at wheel surface. Sign convention: positive = forward.
166|
167|### 5.3 `body/odom` (motor_controller → Jill)
168|
169|Dead-reckoned pose from encoder integration. Frame: robot starting position at origin, x-forward, y-left, theta CCW from x.
170|
171|```json
172|{
173|  "ts": 1713264000.123456,
174|  "x": 0.0,
175|  "y": 0.0,
176|  "theta": 0.0,
177|  "vx": 0.0,
178|  "vtheta": 0.0,
179|  "left_ticks": 0,
180|  "right_ticks": 0,
181|  "dt_ms": 20
182|}
183|```
184|
185|- `x`, `y`: meters from origin.
186|- `theta`: radians, normalized to [-π, π].
187|- `vx`, `vtheta`: instantaneous velocity estimates.
188|- `left_ticks`, `right_ticks`: raw cumulative encoder counts. Allows Jill to do her own integration if desired.
189|- `dt_ms`: time since last odom publication.
190|

292|## 6. Process Specifications
293|
294|### 6.1 `motor_controller`
295|
296|**Responsibility:** Translate velocity commands into PWM output. Read encoders. Publish odometry.
297|
298|**Hardware ownership:** MDD10A (4 GPIO pins), encoder inputs (4 GPIO pins).
299|
300|**Loop structure:**
301|- Main loop at 50 Hz (20ms cycle).
302|- Each cycle: read encoders → compute odometry → check for cmd timeout → compute PWM from latest command → write GPIO → publish odom and motor_state.
303|- Zenoh subscription callback for `cmd_vel`, `cmd_direct`, `emergency_stop` sets shared state variables (protected by a simple lock since callbacks run on Zenoh's internal thread).
304|
305|**Differential drive math:**
306|```
307|wheel_base = W  (meters, measured)
308|wheel_radius = R  (meters, measured)
309|
310|From cmd_vel (linear v, angular ω):
311|  v_left  = v - (ω * W / 2)
312|  v_right = v + (ω * W / 2)
313|
314|PWM mapping:
315|  pwm = clamp(velocity / max_wheel_velocity, -1.0, 1.0)
316|  direction = "fwd" if pwm >= 0 else "rev"
317|  duty_cycle = abs(pwm)
318|```
319|
320|**Odometry integration:**
321|```
322|From encoder ticks since last cycle:
323|  d_left  = left_ticks * (2π * R / ticks_per_revolution)
324|  d_right = right_ticks * (2π * R / ticks_per_revolution)
325|  d_center = (d_left + d_right) / 2
326|  d_theta  = (d_right - d_left) / W
327|
328|  x     += d_center * cos(theta + d_theta/2)
329|  y     += d_center * sin(theta + d_theta/2)
330|  theta += d_theta
331|```
332|
333|**Configuration (constants at top of file, move to config file later):**
334|```
335|WHEEL_BASE_M = 0.0         # measure during build
336|WHEEL_RADIUS_M = 0.0       # measure during build
337|TICKS_PER_REV = 1920        # Pololu 4752: 64 CPR × 30:1 gear ratio
338|MAX_WHEEL_VEL_MS = 0.0     # determine experimentally (330 RPM no-load × wheel circumference)
339|LOOP_HZ = 50
340|CMD_TIMEOUT_MS = 500
341|PWM_FREQUENCY_HZ = 1000
342|```
343|
344|**Encoder counting (software, initial implementation):**
345|Uses `lgpio` edge callbacks on both A and B channels per motor for quadrature decoding. At full speed (330 RPM), edge rate is ~10.5 kHz per motor. Python callback overhead may cause missed counts at high speeds. Acceptable for initial development at typical indoor speeds (50–150 RPM, ~1.6–4.8 kHz). Monitor odometry drift under load as a health indicator.
346|
347|**Known upgrade path:** If software counting proves lossy, add a Raspberry Pi Pico as a dedicated encoder counter (and optionally PWM driver). The Pico communicates cumulative tick counts to the Pi over USB serial. The motor_controller process swaps GPIO reads for serial reads; the Zenoh interface does not change. Chassis design should reserve physical space for a Pico on the compute layer.
348|
349|**Stub deliverable:** A Python script that connects to Zenoh, subscribes to `cmd_vel` and `cmd_direct`, prints received commands, publishes synthetic odom at 50 Hz with incrementing timestamps and zero motion, publishes motor_state. No GPIO access.

OK: 460|## 8. Desktop-Side Assumptions
461|
462|The following assumptions apply to the desktop agent (Jill / CW) and are **out of scope** for this project but must be satisfied for the system to function:
463|
464|1. **Zenoh connectivity.** The desktop must connect to the Zenoh router running on the Pi at `tcp://<pi-ip>:7447`. This may require a new Zenoh session configuration in the CW infrastructure or a new "robot" tool/skill that manages the connection.
465|
466|2. **Heartbeat publication.** Jill (or a CW-side robot interface module) must publish `body/heartbeat` at ≥2 Hz whenever she expects the robot to be active. If she stops publishing, the robot stops moving. This is by design.
467|
468|3. **Command publication.** Jill publishes `body/cmd_vel` to drive the robot. She is responsible for rate-limiting her own commands sensibly (10–20 Hz is reasonable). She must respect the timeout semantics — if she wants the robot to keep moving, she must keep publishing.
469|
470|4. **Subscription and interpretation.** Jill subscribes to `body/odom`, `body/lidar/scan`, `body/oakd/imu`, `body/oakd/depth`, `body/status`, and `body/motor_state` as needed. She is responsible for interpreting these in her OODA loop.
471|
472|5. **Coordinate frame.** The robot's coordinate frame is: x-forward, y-left, z-up, angles CCW from x-axis. Odometry origin is the robot's position at boot time. Jill must manage any world-frame transforms on her side.
473|
474|6. **No guaranteed delivery.** Zenoh pub/sub is best-effort. Messages can be lost, especially over wifi. Jill should not depend on receiving every scan or odom update. The `cmd_vel` timeout mechanism handles the inverse case (lost commands → robot stops).
475|
476|7. **Emergency stop acknowledgment.** When `body/emergency_stop` fires, the robot will not move until heartbeat recovers AND a new `cmd_vel` is received. Jill should treat emergency stop as a state requiring explicit re-engagement, not automatic recovery.

500|- **Motor driver current sensing:** The MDD10A does not provide current feedback. If motor stall detection is needed later, it will require additional hardware (e.g., INA219 on I2C).

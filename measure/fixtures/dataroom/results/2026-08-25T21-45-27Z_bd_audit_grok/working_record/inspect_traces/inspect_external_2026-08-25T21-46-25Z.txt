12|## 1. Purpose
13|
14|Body is the onboard software stack for a differential-drive robot chassis. It provides sensor acquisition, motor control, and safety supervision as a set of independent communicating processes linked by Zenoh. The desktop agent (Jill, running on the CW workstation) connects to the same Zenoh network and interacts with Body exclusively through published topics. Body has no knowledge of Jill's internals; Jill has no knowledge of Body's process structure. The Zenoh topic schema defined in this document is the contract between them.
15|

19||---|---|---|
20|| Cytron MDD10A dual 10A motor driver | GPIO: 2x PWM + 2x DIR | Channel A = left motor, Channel B = right motor |
21|| Pololu #4752 30:1 gearmotor w/ encoder (x2) | GPIO: 2x quadrature (A/B per motor) | 64 CPR motor shaft, 1920 CPR output shaft. 330 RPM no-load @ 12V. Stall: 14 kg·cm / 5.5A |

23|| OAK-D-Lite | USB3 (DepthAI) | Stereo depth, RGB, onboard IMU (BNO086) |

80|### 3.2 Design Principles
81|
82|- Each process is a standalone Python script with its own `main()` and Zenoh session.
83|- No shared memory, no threading across process boundaries.
84|- Processes do not import each other. The Zenoh topic schema is the only coupling.
85|- Every process logs to stdout. The launcher captures and tags output.
86|- Every process handles SIGTERM gracefully: releases hardware, closes Zenoh session, exits.

131|## 5. Message Schemas
132|
133|All messages are JSON-encoded UTF-8 strings published as Zenoh values. Timestamps are Unix epoch float (seconds with microsecond precision). All spatial units are SI: meters, radians, meters/second, radians/second.
134|
135|### 5.1 `body/cmd_vel` (Jill → motor_controller)
136|
137|Twist command in robot body frame. Linear is forward/back, angular is rotation (positive = counterclockwise viewed from above).
138|
139|```json
140|{
141|  "ts": 1713264000.123456,
142|  "linear": 0.2,
143|  "angular": 0.0,
144|  "timeout_ms": 500
145|}
146|```
147|
148|- `linear`: m/s, positive = forward. Clamped by motor_controller to hardware limits.
149|- `angular`: rad/s, positive = CCW.
150|- `timeout_ms`: if no new `cmd_vel` arrives within this window, motor_controller sets output to zero. Safety backstop independent of watchdog.
151|
152|### 5.2 `body/cmd_direct` (Jill → motor_controller)
153|
154|Direct wheel velocity command. Bypasses twist-to-differential math. For calibration and testing.
155|
156|```json
157|{
158|  "ts": 1713264000.123456,
159|  "left": 0.15,
160|  "right": 0.15,
161|  "timeout_ms": 500
162|}
163|```
164|
165|- `left`, `right`: m/s at wheel surface. Sign convention: positive = forward.
166|
167|### 5.3 `body/odom` (motor_controller → Jill)
168|
169|Dead-reckoned pose from encoder integration. Frame: robot starting position at origin, x-forward, y-left, theta CCW from x.
170|
171|```json
172|{
173|  "ts": 1713264000.123456,
174|  "x": 0.0,
175|  "y": 0.0,
176|  "theta": 0.0,
177|  "vx": 0.0,
178|  "vtheta": 0.0,
179|  "left_ticks": 0,
180|  "right_ticks": 0,
181|  "dt_ms": 20
182|}
183|```
184|
185|- `x`, `y`: meters from origin.
186|- `theta`: radians, normalized to [-π, π].
187|- `vx`, `vtheta`: instantaneous velocity estimates.
188|- `left_ticks`, `right_ticks`: raw cumulative encoder counts. Allows Jill to do her own integration if desired.
189|- `dt_ms`: time since last odom publication.
190|

292|## 6. Process Specifications
293|
294|### 6.1 `motor_controller`
295|
296|**Responsibility:** Translate velocity commands into PWM output. Read encoders. Publish odometry.
297|
298|**Hardware ownership:** MDD10A (4 GPIO pins), encoder inputs (4 GPIO pins).
299|
300|**Loop structure:**
301|- Main loop at 50 Hz (20ms cycle).
302|- Each cycle: read encoders → compute odometry → check for cmd timeout → compute PWM from latest command → write GPIO → publish odom and motor_state.

325|  d_center = (d_left + d_right) / 2
326|  d_theta  = (d_right - d_left) / W
327|
328|  x     += d_center * cos(theta + d_theta/2)
329|  y     += d_center * sin(theta + d_theta/2)
330|  theta += d_theta
331|```

9|- **OAK-D-Lite IMU:** retail units usually include a BNO IMU; DepthAI may require `oakd.imu_enable_firmware_update: true` (default in [config.json](config.json)) on first use. Some **Kickstarter OAK-D-Lite** boards have **no IMU** ([Luxonis docs](https://docs.luxonis.com/software-v3/depthai/depthai-components/nodes/imu/)) — set **`imu_hardware_present`: false** to run `oakd_driver` with synthetic `body/oakd/imu` so the launcher does not crash.
10|- A Zenoh **router** (`zenohd`) reachable by every Body process and every client (teleop or Jill). On the robot, run the router on the Pi and listen on TCP **7447** (see [Configuration](#configuration)).

43|### Starting `zenohd` (router)
44|
45|Body expects a **router** already running before you start `body.launcher` or `teleop`.
46|
47|**`zenohd` is not installed by `pip` or your `.venv`.** The Python package `eclipse-zenoh` is only the client library. If the shell says `zenohd: command not found`, install the router binary below (or add it to your `PATH`).
48|
49|1. **Install the router binary** on the machine that runs the router (usually the Pi). Pick one:
50|   - Official options: [Zenoh installation](https://zenoh.io/docs/getting-started/installation/).
51|   - **Raspberry Pi 5 (64-bit):** use the **aarch64 Linux standalone** archive from [eclipse-zenoh/zenoh releases](https://github.com/eclipse-zenoh/zenoh/releases). Unpack so `zenohd` and the bundled `*.so` plugins stay in the **same directory** (the archive layout is flat). Example (adjust `ZV` to match your `eclipse-zenoh` major.minor, e.g. `1.9.0`):
52|
53|bash
54|ZV=1.9.0
55|curl -sLO "https://github.com/eclipse-zenoh/zenoh/releases/download/${ZV}/zenoh-${ZV}-aarch64-unknown-linux-gnu-standalone.zip"
56|mkdir -p "$HOME/zenoh/${ZV}"
57|unzip -o "zenoh-${ZV}-aarch64-unknown-linux-gnu-standalone.zip" -d "$HOME/zenoh/${ZV}"
58|
59|
60|2. **Config:** This repo includes [deploy/zenohd-router.json](deploy/zenohd-router.json) — listens on **TCP `0.0.0.0:7447`**.
61|
62|3. **Run** from the directory that contains `zenohd` (foreground; use `tmux` / `systemd` for production). Example if Body lives at `~/Body`:
63|
64|bash
65|"$HOME/zenoh/1.9.0/zenohd" -c "$HOME/Body/deploy/zenohd-router.json"
66|
67|
68|To put `zenohd` on your `PATH`, copy **both** `zenohd` and the `libzenoh_plugin_*.so` files into the same target directory (e.g. `$HOME/zenoh/1.9.0` already does), then:
69|
70|bash
71|export PATH="$HOME/zenoh/1.9.0:$PATH"
72|zenohd -c "$HOME/Body/deploy/zenohd-router.json"
73|
74|
75|If your `zenohd` build only accepts JSON5 configs, copy `zenohd-router.json` to `zenohd-router.json5` and pass that path.
76|
77|4. **Check:** With `zenohd` running, start `body.launcher` on the Pi; processes should connect to `tcp/127.0.0.1:7447` per [config.json](config.json).

100|## Running the stack (`body.launcher`)
101|
102|On the **Pi** (after `zenohd` is up):
103|
104|bash
105|cd /path/to/Body
106|export PYTHONPATH="$(pwd)"
107|.venv/bin/python -m body.launcher
108|
109|
110|Startup order: `watchdog` → `motor_controller` → `lidar_driver` → `oakd_driver`. Logs are prefixed by process name.
111|
112|**Stop:** `Ctrl+C` or `SIGTERM` to the launcher; it sends `SIGTERM` to children, waits, then `SIGKILL` if needed.
113|
114|**Restarts:** If a child exits unexpectedly, the launcher restarts it with exponential backoff (capped at 30 s).
115|
116|**Deploy tip:** If errors reference old line numbers or missing symbols (e.g. `XLinkOut` on DepthAI v3), the Pi’s `~/Body` tree is behind your main repo—`git pull` or rsync the updated `body/` tree, then restart the launcher.
117|
118|**Watchdog:** Until something publishes **`body/heartbeat`** (e.g. `body.teleop`), the watchdog may emit **`body/emergency_stop`** (`heartbeat_timeout`). That is expected; start teleop or another client when you want the stack to see a live operator.

152|### Teleop REPL
153|
154|| Command | Meaning |
155||---------|---------|
156|| `vel LINEAR [ANGULAR]` | Latch `body/cmd_vel`: linear m/s, angular rad/s (CCW positive). Angular defaults to `0`. |
157|| `stop` | Latch zero velocity. |
158|| `status` | Print last `body/status` JSON (if any). |
159|| `help` | Short help. |
160|| `quit` / `q` | Exit teleop (heartbeat and cmd_vel stop; robot may e-stop if nothing else publishes heartbeat). |
161|
162|Optional flags: `--heartbeat-hz` (default 2), `--cmd-vel-hz` (default 20), `--timeout-ms` (default 500), `--verbose` (print every `body/status`).
163|
164|**Motion authority:** Do **not** run teleop and another publisher (e.g. Jill) both commanding `body/cmd_vel` at the same time; the motor side effectively sees interleaved commands.
165|
166|## Integration expectations (Jill / other agents)
167|
168|Any desktop agent that embodies this robot should:
169|
170|- Publish **`body/heartbeat`** at ≥ **2 Hz** while the robot is expected to accept motion.
171|- Publish **`body/cmd_vel`** often enough to satisfy the message **`timeout_ms`** (default **500 ms** in the spec) while moving or holding speed.
172|- Subscribe to `body/odom`, `body/lidar/scan`, `body/oakd/*`, `body/status`, `body/motor_state`, etc., as needed.
173|
174|After a heartbeat fault, recovery follows **§5.10** in [body_project_spec.md](body_project_spec.md) (heartbeat back and a new `cmd_vel` path as implemented on the Pi).
175|
